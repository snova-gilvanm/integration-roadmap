What the Radar is for

Stay ahead of the tools developers adopt, so SambaNova is integrated before customers ask.

The Radar looks outward. The Board and Timeline track committed work; the Radar finds what should be committed next. It has three views:

  • Trending tools ranks popular open-source tools that have no SambaNova guide yet, on visibility, usage and reliability.
  • Competitor gaps lists tools that Cerebras, Groq, Together, Fireworks, Novita, xAI or DeepSeek document as integrations and that we don't have live.
  • Signals log is where a candidate lands once someone thinks it matters, from either list above or from a customer ask, Slack thread or event.

How a candidate moves forward: Add to signals, discuss at the integrations review, open a child ticket under CP-1521, score it in Stack rank, then give it a delivery window. Nothing on the Radar is committed work.

How the trending list was chosen

The 46 tools were selected by hand on , using these rules:

  1. Same categories as our catalog: coding agents and editors, agent and app frameworks, chat apps, RAG and data, automation, evaluation and observability, safety, browser and sandbox, voice.
  2. Not already covered: anything live on docs.sambanova.ai, in review, or slotted on the roadmap is excluded (for example LangChain, Cursor, Mastra, Pydantic AI).
  3. Open source with a public GitHub repo, so stars, releases and commits can be measured the same way for every tool.
  4. Known traction: roughly 5k GitHub stars or more, or a high-volume package.
  5. Included on purpose: tools where a SambaNova provider was already merged upstream through a past ticket but no guide exists (goose, smolagents, Hermes Agent, DeerFlow), and tools that competitors document (see Competitor gaps).

What it is not: an exhaustive market scan. Closed-source products (Windsurf, GitHub Copilot, Raycast) can't be scored on these metrics and appear under Competitor gaps instead. Gemini CLI is kept for its visibility even though no custom-endpoint route is documented.

How the score is calculated

Each signal becomes a 0 to 100 value, then the score is a weighted mean.

Visibility = (log10(stars) - 3) / 2.3 x 100 1k stars = 0, 200k = 100 Usage = (log10(downloads/mo) - 4) / 3.7 x 100 10k/mo = 0, 50M/mo = 100 Reliability = mean of the parts available: Release recency 30 days 100 · 90 days 75 · 180 days 50 · 1 year 25 · older 0 Commit activity log10(commits/mo + 1) / log10(500) x 100 Contributors log10(contributors) / log10(500) x 100 Reviews = (rating - 1) / 4 x 100 Score = (Visibility x 30 + Usage x 25 + Reliability x 30 + Reviews x 15) / (sum of weights for the signals present) x 0.9 when there is no download metric

All values are capped between 0 and 100.

Why these choices

  • Log scales: stars and downloads span four orders of magnitude. A linear scale would let two or three giants flatten everyone else.
  • Visibility and reliability weigh most (30 each): you asked for visible, reliable tools. A popular but abandoned project is a poor integration bet.
  • Usage 25: downloads show real adoption, but only exist for tools that ship a package.
  • Reviews 15: valuable but manual and sparse, so they adjust the order rather than drive it.
  • Missing data is left out, not guessed. The 10% penalty keeps tools without a download count from ranking above comparable tools that have one.

Worked example, Firecrawl: 186k stars gives Visibility 99. 5.3M downloads a month gives Usage 74. Reliability is the mean of release recency 50 (June release), commits 79 (135 a month) and contributors 82 (163), which is 70. Score = (99 x 30 + 74 x 25 + 70 x 30) / 85 = 81.

How competitor gaps were found

  1. Read each provider's integrations index on : Cerebras, Groq, Together AI, Fireworks AI, Novita AI and xAI official docs, plus the community list awesome-deepseek-integration. Each card under Competitor gaps links to the list used.
  2. Kept only third-party tools. Provider features (BYOC, docs MCP), consumer app connectors (Gmail, Drive) and sandbox networking examples were dropped.
  3. Matched names to ours, merging aliases (Copilot CLI, Copilot App and VS Code Copilot Chat count as GitHub Copilot; AutoGen (AG2) counts as AG2).
  4. Parity = how many of a provider's listed integrations we also have live, divided by their total.
  5. Gaps table = tools listed by at least one provider and not live with us, sorted by how many official providers list them. "+ DS" means the DeepSeek community list also has it.

Limits to keep in mind

  • Snapshot, not live. Metrics and competitor lists are from . They change monthly; refresh before using them in a decision.
  • Expected routes are unverified. The mode shown for each tool (OpenAI-compatible, built-in provider and so on) is what its docs suggest, until someone tests it.
  • Hermes Agent shows 251k stars and 11k commits a month as reported by GitHub. Confirm before quoting.
  • DeepSeek list was read partly, because of its length, and is community curated. Novita was read from its docs index only.
  • Stars can be inflated by launches and campaigns. Read them together with downloads and release activity.
  • Customer demand beats every metric. A single paying customer ask in the Signals log outranks a high score.

Refresh: ask Claude to "refresh the Radar metrics and competitor lists" to rerun the pull and republish. A monthly scheduled refresh can be set up.

Tiers and cadence

Last maintained is the latest Jira ticket labelled maintenance closed for the asset. Critical and high assets without one fall back to the guide's last docs update, shown as such. Medium and low assets use whichever is later.

Proposals appear on their own when an asset is overdue, due within 30 days or has no record, and no maintenance ticket is open for it. Anyone can add one by hand. Approve a proposal to mark it for Jira, then ask Claude to create the approved ones under CP-1521 with the maintenance label.

How the score works

Criticality = tier: Critical 5, High 4, Medium 2, Low 1 Exposure = 1 to 5, set by the team in the table above Urgency = time since last maintenance / cadence under 50% 1, 50 to 80% 2, 80 to 100% 3, 100 to 150% 4, over 150% or no record 5 Score = (Criticality/5 x 40 + Exposure/5 x 30 + Urgency/5 x 30) / (weights of the signals present) x 100
  • Customer defects and bugs jump the queue, whatever their score.
  • Exposure is left out, not guessed, until someone rates it. Rate the assets customers use most so they rise.
  • Owner flags mark open tickets with no assignee or an assignee whose Jira account is inactive.

How an integration moves through the roadmap

STEP 1IntakeAn ask from a customer, partner or the community becomes a child ticket of CP-1521. Asks that are not a ticket yet live on the Radar, along with trending tools and gaps against other providers.
STEP 2Research the doorConfirm how the tool can reach SambaNova: built-in provider, OpenAI or Anthropic compatible endpoint, SDK, adapter, or a partner motion. Closed doors are confirmed in writing before engineering starts.
STEP 3Rank and slotBacklog items are scored in Stack rank, then given a delivery window label (int-oct-2026 to int-q2-2027) against docs and engineering capacity.
STEP 4Build, validate, publishWorking configuration, a guide PR to sambanova/docs, review, merge, then the Japanese translation. Upstream provider PRs are tracked to merge.

Sources and refresh

Jira, epic CP-1521. Ticket status, owner, window label and due date. Viewers with the Atlassian connector see statuses refresh live every 5 minutes; everyone else sees the snapshot dated in the header. Goals and deliverables come from each ticket's description and its "Expected outcome".

docs.sambanova.ai. Every "Live" row links to its published guide under /docs/en/integrations/.

Radar metrics. GitHub stars, releases, commits and contributors, and PyPI or npm downloads, pulled through shields.io, plus the integration lists of six other providers. The Radar tab has a "How the Radar works" view with the full method and formulas.

Maintenance. Jira tickets under CP-1521 labelled maintenance, linked to an inventory of assets built from the docs guides and their integration modes, plus internal repos named in tickets. Each tier has a cadence: critical every 2 months, high every 3, medium every 6. The Maintenance tab explains the score.
